## 3.6.2（2026-11-20）失败可诊断性：hint + 清单题录回填（3.6.1 实跑暴露）

**起因**：一次真实取全文任务里，调用方把「出版商 403 / 网络错」误判为「这篇没有 OA 版本」，据此收手；同时交付的待下载清单题名与年份全空，用户拿着无法继续。两处都不是抓取能力问题，是**失败输出不可执行**。

| # | 现象（本机实测） | 修法 |
|---|---|---|
| 1 | `fetch` 失败输出只有 `reason`/`attempts`，不写「下一步能做什么」 | 新增 `hint` 字段，按 reason 分流给出：显式代理重试 / 换 OA 绿版 / 转 L3 人机校验 / 回填题录。**只加字段，不改 reason 码、不改既有键** |
| 2 | `checklist` 生成 `| 1 |  | ? / ? | [DOI](...) |` | 对题名或年份为空的条目调 `meta_record` 回填（失败仍保留 DOI 链接，不编造）；返回体新增 `titles_filled` 计数 |
| 3 | 403 常见误判是「无 OA」，而实际多为出口或通道问题 | `hint` 里显式点破「当前为默认直连，可显式指定代理重试」，但不新增 reason 码——单个 403 响应推不出 TLS 指纹，硬编码新码属臆测 |

**实测**：`fetch` 403 → `hint: forbidden_403: 当前为默认直连；可显式指定代理重试（--proxy <url>）…`；`checklist` 单条 DOI → `titles_filled: 1`，清单显示「Machine learning for predicting the outcome of terminal ballistics events / Defence Technology / 2024」。

**边界**：`hint` 只生成建议，不自动改代理、不自动重试；云服务入口仍需调用方自己决策。（诊断里另两条「OpenAlex 漏 locations[]」「下载目录没读注册表」经代码核查为**早已实现**，本次不重复改。）

**回归**：`audit.py` / `run_cases.py` / `run_flow.py` 全绿后交付。

## 3.6.1（2026-11-19）默认移动的四个边界修补（3.6.0 实跑暴露）

**背景**：3.6.0 写完后，用真实知网下载 + 子代理实跑，暴露出四个"默认移动"落地时的边界问题。都不是新功能，是同一行为的补全。

| # | 现象（实测） | 修法 |
|---|---|---|
| 1 | 重复下载（内容已在库）判 `duplicate` / `already_adopted`，不进 `selected` → 源文件留在下载目录 | 移动阶段对这类条目按 MD5 在目标目录找同内容文件，核对一致后同样删源；找不到可核对副本则一律不动 |
| 2 | 整批 `already_adopted`（只来清源）时 `adopted=0`，被"空转即失败"守卫误判成退出码 3 | 守卫改为只看 `status == "new"` 的条目：**只有真有新条目却没落位**才判 3 |
| 3 | 同一 plan 重复执行时源已不在，`unlink` 抛 `FileNotFoundError` → 记成 `source_kept` 失败 | 源不存在时幂等跳过，不再计问题 |
| 4 | `sources_kept` / `not_moved` 用 `len(movable) - len(removed)` 计算，源已不在时仍报"保留 3"，与实际不符 | 改为按"盘上仍存在该源"实时统计 |

**实测验证**（真实机构登录态 + 真浏览器 + 真知网下载，非合成文件）：

| 检查项 | 结果 |
|---|---|
| 下载 4 篇「盐渍土路基」期刊论文 | 全部 KDH 2.00，1.0–1.9 MB |
| `adopt` | `adopted=4`，`sources_removed=4`，`problems=0` |
| 下载目录 | 跑前 14 项 → 跑后 **14 项**，`.caj` 0 个，无 `.crdownload` |
| `verify` | `records=4, matched=4, missing=0` |
| `check` | `valid=true, format=kdh, requires_reader=CAJViewer/E-Study` |

**回归**：`run_flow.py` 15 → **16 条**（新增"重复下载也清走源"）；`run_cases.py` 33 条；`audit.py` 23 通过。

## 3.6.0（2026-11-19）下载后默认移入工作区（**下载行为变更**，故升 minor）

**起因**：作者本人也记成"下载完自动移到工作区"，实测却发现下载目录留了 3 个 `.caj`。查证后确认：从 3.1.0 起默认一直是**复制**，`--move-sources` 只是可选的"移到隔离区"。而 `SKILL.md` 只解释了这个参数、**从没写过默认值**——文档缺失导致连作者都误判。这个缺口的修正本身就是本次改动的正当理由。

**新行为**

| 项 | 改前 | 改后 |
|---|---|---|
| `adopt` 默认 | 复制到工作区，源原地不动 | **复制 → 校验 MD5 → 删源**（顺序不可颠倒） |
| 保留源 | 默认即是 | `--keep-sources` 显式指定 |
| 旧参数 | `--move-sources` 移到隔离区 | 保留为兼容别名，旧语义废弃 |
| 删源失败 | 无此路径 | `source_kept:<原因>` + 退出码 3（副本已在，源未删） |
| `rollback` | 隔离区移回 + 工作区副本丢 `.trash` | **把工作区副本移回原路径**；同名被占用则写 `.restored`，不覆盖 |
| 隔离区 | 默认流程会用 | 不再默认使用，老批次仍可 `purge` |

**只动该动的**：只处理 `src_map` 里有记录的条目（= 本次真正落位的那条），**plan 之外的文件一律不碰**。下载目录里的安装包、压缩包等历史文件不受影响。

**为什么不用 `shutil.move` 直接搬**：跨盘 move 内部是"复制 + 删除"两步，中途失败会两边都不完整；改成"先复制、校验一致、再删源"，最坏情况只是多留一个源文件，永远不会丢数据。

**验证**：`run_flow.py` 11 → **15 条**（默认移走 / rollback 复原 / `--keep-sources` 保留 / 仍正常落盘），全通过；`run_cases.py` 30 → **33 条**（新增 M01–M03 锁住文档与源码契约）。

## 3.5.4（2026-11-19）修机构订阅通道的格式闸门：KDH/CAJ 不该被判"不是 PDF"

**起因**：按"有机构订阅时用这个技能"的真实场景实测（知网 + 用户所在高校的机构登录态）。

**实测链路**（全程串行，每站只点一次）：

| 步骤 | 结果 |
|---|---|
| 机构登录态 | 检索页右上角有机构名，且所有行 `title="下载"`，无"未登录"标记 |
| 检索 | `冻融循环路基` → 1,376 条 |
| 下载 | 点击下载图标后 **约 1 秒**落盘 `…_张淑梅.caj`，2,135,395 B |
| 真实格式 | 魔数 `KDH 2.00`——**后缀是 `.caj`，内容是 KDH** |

| `scan-new` → `adopt` → `verify` | selected=1 → adopted=1（自动改名为 `.kdh`）→ 1/1 matched ✅ |

**问题**：§5 第 3 步要求"过魔数闸门才落盘"，而闸门只认 `%PDF`。**机构订阅的主通道恰恰给 KDH/CAJ**——照文档执行，会把一次成功的订阅下载判成失败。

- `SKILL.md` §5 第 3 步写明"PDF、KDH、CAJ 都算通过；非 PDF 标「需阅读器」"。
- 新增用例 `H01`（KDH 判有效）/ `H02`（HTML 伪装仍失败）。

**未改**：交付仍要求注明"需官方阅读器"（3.5.3 已加）；KDH 转 PDF 不做（需第三方工具，属格式逆向）。

**验证**：`audit.py` 23 通过；`run_cases.py` 30 通过；`run_flow.py` 11 通过；`SKILL.md` 15,046 字节。

## 3.5.2（2026-11-18）按实测修路由与出口：顶层 reason 不可分流、静默空转、退出码不传 shell

**起因**：一次外部客观测试（A 组不知情 / B 组按文档 / 无技能对照组，共 30 条冻结用例）。硬门禁 5/5 通过，但路由与交付层暴露出四个可复现的确定性缺陷——它们的共同点是「**失败或空结果对调用方不可见**」。

### 1. 顶层 `reason` 无法分流（路由层，最严重）

- 现象：`fetch` 只要候选 ≥1 且全失败，顶层 `reason` 恒为 `no_candidate_passed`，真实原因（`captcha` / `network_error:*` / `html_landing`）只在 `attempts[].reason`。文档却教执行者「L2 失败看 `reason`」→ 分流表实际读不到值。
- 实测：3 个 DOI 中 2 个顶层为 `no_candidate_passed`，实际原因分别是 `captcha` 与 `SSLEOFError`。
- 改动：`oa_fetch.py` 新增 `_top_reason()`——**单候选失败时顶层直接给出该候选原因**，多候选才用 `no_candidate_passed`；`SKILL.md` §2.1 与 `discovery.md` §3.2 明确「分流看 `reasons[]` / `attempts[].reason`」。

### 2. reason 码表覆盖不全（文档与脚本漂移）

- 脚本可产出 19 个码，`discovery.md` 表里只有 10 个；`json_error_body` / `not_pdf*` / `too_large` / `partial_suffix` / `missing` / `no_candidate_passed` 全部缺表。
- 改动：两处 reason 表补全到 19 个；新增回归用例 `B01` 用 AST 抽出脚本的 reason 集合，**任何一个码没进 SKILL.md 就 FAIL**。

### 3. 交付链静默空转 + 退出码不传 shell

- `scan-new`（文档原样命令）对 L2 直取文件默认判 `manual_drop`、`selected=0`；随后 `adopt` 返回 `adopted=0` 而**退出码 0**。原因是这类文件没有浏览器下载记录，需 `--allow-unconfirmed`——而 SKILL.md 从没提过这个参数（只在 `toolchain.md`）。
- 更根本：`litadopt.py` / `fetch_cn_journal.py` 的 `main()` 没把 `exit_code` 传给 shell，`verify` 报 4 时进程仍退出 0，任何脚本编排都看不见失败。
- 改动：① 三个脚本 `sys.exit(main() or 0)`，`litadopt` 用 `LAST_CODE` 回传 emit 的退出码；② `adopt` 在「有目标却一条没落位」时退出 3；③ `SKILL.md` §6 补 `--allow-unconfirmed` 与 `adopted=0` 判失败；
- ④ `verify` 不再把**已 rollback 批次**的 dst 算成 missing（原先正常回滚必红）。

### 4. L1.5 静默丢弃 + L3 无确定性出口

- `fetch_cn_journal.py` 对「前缀不在内置刊名表」「DOI 不以 10. 开头」「类别 A/B」三种情况**静默跳过**，输出空数组、退出 0，与「本来就没有目标」无法区分。
- 改动：跳过行写入 `status`（`skipped_no_template` / `skipped_bad_doi` / `skipped_category`）+ `reason`，退出码 3。
- 新增 `SKILL.md` §10「确定性出口」：L3 不可用时交付清单写 `degraded_to_l1_6: true` + `degraded_reason`（`no_browser` / `no_auth` / `unsupported`），部分失败写 `ok:false` + `fail_reason`（四值枚举），全失败写 `all_fulltext_failed`。

### 5. 文档层修正

- 消除两处内部冲突：`limits.md` 的「遇订阅页立即停」与 `discovery.md` 的「`paywall_landing` → L3」按**用户有没有权限**拆开；403/429 的重试口径统一为「403 不重试、429 退避 1 次」。
- 33% OA 命中率改口径：n=3 小样本、仅作量级参考，与第三方 123-DOI 数据的对应关系标为**待验证假设**。
- `SKILL.md` 15,736 → **15,351 字节**（description 716 → 440 字符）；批量与专项命令移入 `references/commands.md`。
- 新增 `tests/`：`cases.yaml`（27 条声明式用例）+ `run_cases.py` + `run_flow.py`（交付链沙箱测试，11 条）。改任何描述或逻辑后跑一遍，非 0 即 block。
- `toolchain.md` §4 补「点了下载但目录没文件」的判定节奏：**≤30 秒无中间态才重看页面，90 秒才记需人工**（实测两次落盘相隔约 60 秒）。



### 6. 回归期新发现：`meta` 的 `ok:true` 会被当"拿到全文"

- 同一篇订阅刊：`fetch` 是 `ok:false` + exit 3，`meta` 却是 `ok:true` + exit 0，而输出里一个字都没说"全文未获取"（源码 `rec["ok"] = bool(title or links)`）。两个 `ok` 语义不同、字段名相同，调用方极易误判。
- 改动：`meta` 输出新增 `fulltext: false` 与 `deliverable: "metadata_only"`，Markdown 末尾加一行「全文：**未获取**」；SKILL.md §7 注明「`meta` 的 `ok:true` 只代表题录可取」。
- 另：`resolve` 的 `ok:true` 会掩盖 `notes` 里的 `openalex:network_error:URLError`（本次未改，记为已知缺口）。
- 用例增至 **27 条**（新增 `G01` 源码契约、`G02` 文档契约）。

## 3.5.1（2026-11-18）写清**能力依赖机构登录态** + SKILL.md 结构精简 + 触发词收紧

### 5. 触发词收紧：23 个平铺 → 强/弱两层

**问题**：原描述把 23 个词平铺成一个列表，其中 5 个有误触发风险——`能不能下`（任何下载询问都命中，如"这软件能不能下"）、`高级检索`（通用功能名，如查工商信息）、`检索式`（专利/情报也在用）、单平台名 `arXiv`/`知网`/`万方`（提到不等于要抓取）、`已登录浏览器`（与通用浏览器操作重叠）。

**改法**：

| 层级 | 判定 | 词表 |
|---|---|---|
| **强触发** | 单独出现即触发 | 查文献、检索文献、搜论文、找文献、下载论文、下载文献、文献综述、文献归集、导出题录、OA 全文、浏览器取全文、这篇能不能下 |
| **弱触发** | 须与"文献/论文/期刊/全文/DOI"**同句共现**才触发 | 知网、CNKI、万方、维普、Web of Science、PubMed、arXiv、ScienceDirect、Google Scholar、高级检索、检索式、已登录浏览器 |

- `能不能下` → **`这篇能不能下`**，必须有文献指代；已有"下载论文/下载文献"覆盖正常说法。
- 平台名降为弱触发：聊到"arXiv 上有个新模型"不该触发抓取，但"arXiv 上找这篇论文全文"会命中。
- `不适用于` 补全：新增**软件/视频/素材下载**、**专利与标准检索**，与原有的通用抓取/表单/测试/商品社媒并列。
- 顺带修正 `description_zh` / `description_en` 里遗留的"四级路由"（正文早已改为五通道，描述层漏改）。

**取舍**：弱触发靠"同句共现"判断，理论上会漏掉"帮我下这篇：<链接>"这类无关键词的指令。这类请求本就不会被任何词表覆盖，实际依用户显式点名技能或上下文判定，不靠扩充词表解决——词表越宽，误触发越多。
